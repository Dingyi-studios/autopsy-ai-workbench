# 架构与开发路线

## v0.1：先把证据上下文交接做好

本版新增一个独立 Node.js CLI，使用 Autopsy 4.23.1 的现有本地 MCP 查询功能，不修改案件数据库。采集后的元数据保留原始字段，并附带本次导出范围内唯一的引用。输出只写到使用者指定的本地目录。

关键边界：这是有限数量的预览，不是全量证据抽取、正文检索、相关性排序或专家分析。当前上游 `caseId` 来自案件显示名，不能当作稳定身份。`totalArtifacts` 也不能直接用来证明某一类工件查询已覆盖全部材料。

## 下一阶段：Java Bridge 与来源服务

1. 为案件建立稳定身份，区分案件、数据源、快照和分析运行；切换案件时使旧绑定失效。
2. 提供基于稳定键的分页快照导出，记录尾页、数量、重复、失败和不支持的数据；不能依靠反复调用有上限的预览实现全量导出。
3. 正文解析保存原始哈希、解析器版本、页码、行号、记录主键或字节位置。只有真正读取过的来源才签发可引用位置。
4. 将发现、解析、索引和分析覆盖率分开记录；加密、损坏、未知格式和部分成功均保留可见状态。
5. 在独立服务中实现结构化过滤、全文检索及必要的向量召回，再对案件级隔离和中文召回做评估。

## 专家接入

后续以统一适配层接入自有专家服务：提交任务、流式进度、取消、结果和错误。专家必须交换结构化发现、支持来源、反证、假设及缺口，不能只交换自然语言讨论记录。

优先接入证据复核与文书通信，跑通一件合成案件的来源阅读、分析、人工审核和报告闭环。资金、流量、内存、服务器、APK 和 EXE 分析按专用工具及授权条件逐步接入。角色简报不等于已有模型权重或解析引擎。

## 验收顺序

- Windows 实机确认现有 MCP 连接、数据形状和案件切换行为。
- 用超过 500 条记录的样本验证分页与数量对账，明确无法处理的范围。
- 所有显示的来源引用能回到对应原文位置；来源存在与语义支持分别验证。
- 对每条案件发现分开记录事实、解释、假设、反证与人工复核状态。
- 在相同材料、预算和问题下比较规则检索、单模型及专家协作，不预设多专家效果更好。

## 公开仓库边界

仅公开本项目原创代码、合成样本和设计文档。商业工具、公司内部接口、真实案件材料及许可不明的逆向产物不随本仓库发布。Autopsy 和第三方组件的原始作者、许可证及声明始终保留。
